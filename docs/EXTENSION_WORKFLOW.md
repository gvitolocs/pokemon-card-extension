# Extension Workflow

## Button Click Flow

1. Marketplace content scripts add a Pokoin button to supported listing pages.
2. Buttons are created immediately in a gray/loading state and still open the Chrome side panel. A resolved match is not required before the user can click.
3. When matches arrive, the button shows `Pokoin.com (N)`, where `N` is the count of matches above the high-confidence threshold. Vinted keeps the Pokoin brand blue in both empty and matched states. Cardmarket switches from a compact gray loading state to a compact bright-blue matched state with a visible border/glow.
4. Clicking any marketplace button opens the Chrome side panel for the current tab instead of opening a new browser tab.
5. The background service worker refreshes the side panel state for the sender tab.
6. The side panel embeds the Pokoin marketplace card page so the user's Pokoin login session stays inside the panel.
7. Marketplace processors use the background service worker as the reliable Cardvault search path. There is no active Supabase client, `config/supabase` module, or direct database lookup in the extension.
8. Button clicks always force a fresh side-panel loading state and resolve the clicked tab URL/title, avoiding stale candidates from previous pages.
9. Vinted, eBay, Cardmarket, and CardTrader all use this same button -> background refresh -> side panel render workflow.
10. Vinted passes selected title and item-description clues with preview searches and button clicks. Selected Pokemon-name-like clues are marked as primary clues, and selected collector-number or expansion chips stay in the structured search title and signature, so toggles force a fresh search with strong card identity evidence instead of reusing stale candidates.
11. CardTrader card URLs already contain the Pokoin/CardTrader blueprint id, so CardTrader button clicks construct side-panel state immediately from the URL id and do not wait for page scraping, Cardvault name resolution, extension search, or autocomplete.
12. Direct CardTrader state stores a human card name for the side-panel header. The header keeps only the card name and real card-name punctuation/variation, such as `Hypno`, `Gengar & Mimikyu GX`, or `Tornadus-EX`, and drops parenthesized expansion/rarity/collector/promo details plus pipe/category/site suffixes from CardTrader titles and URL slugs.
13. CardTrader injects the Pokoin button as a real `type="button"` beside the card title and handles click events in capture phase. The handler prevents default page actions, stops propagation, ignores duplicate clicks while an open request is in flight, and sends a single side-panel message instead of letting CardTrader links/forms/navigation handlers react.
14. Cardmarket buttons are styled as compact inline controls in both gray/loading and bright-blue matched states. Product-page injection waits until Cardmarket has hydrated the stable title container and product identity details (`.page-title-container h1` plus `dl.labeled` fields such as `Numero` and `Stampata in`, or an equivalent expansion link) before inserting into the title action area such as `.ms-auto`. If hydration or AJAX removes the control, a short MutationObserver/retry path re-injects it for the same stable product URL without launching duplicate searches. Relabeling the button after matches are found reapplies the matched color, border/glow, and small Pokoin icon sizing so the raw icon asset cannot stretch across the product image area.
15. Cardmarket scrape observations are sent from the background worker to `POST https://pokoin.com/api/cardmarket-scrape-observation`. The payload contains the parsed `structuredCard`, `cardmarketContext`, selected or best `match`, and `promoteVerifiedLink`. Navigation/search observations are non-promoting; opening the side panel from a matched Cardmarket candidate promotes the verified link and allows Pokoin to store the full Cardmarket URL in `marketplace_cm_verified_links`.
16. Auth for Cardmarket observations uses a minimal Pokoin-origin bridge at `https://pokoin.com/extension/auth-bridge`. The extension injects `pokoin-auth-bridge.js` only on that path, requests a Firebase ID token with `postMessage`, accepts token responses only from `https://pokoin.com`, and stores the token in `chrome.storage.session` with expiry metadata. The token is never stored in `chrome.storage.local` and is not exposed to marketplace content scripts.
17. If a Cardmarket observation is ready before a Pokoin token is available, the background worker queues a small bounded session-only pending observation and opens or reuses the bridge tab in the background. When a valid token arrives, pending observations are flushed with `Authorization: Bearer <token>`.
18. Vinted renders its Pokoin button, clue chips, and candidate preview in a compact transparent fixed overlay marked with `data-pokoin-extension-panel`. The overlay uses Shadow DOM when the browser supports it, with reset styles on the host and inside the shadow tree so Vinted page CSS cannot restyle the Pokoin controls. Overlay buttons are real `type="button"` controls with pointer events enabled; main-button and candidate-row clicks are handled in capture phase, prevent Vinted page navigation handlers from seeing the click, and send one `openSidePanelForCurrentTab` message per activation.
19. Vinted processing is keyed by a stable listing URL that ignores query strings and hashes. Repeated `processProductPage()` calls, MutationObserver callbacks, and same-listing SPA rerenders reattach or reuse the existing owned root instead of creating another button, clue chip group, preview list, or background search.
20. Vinted starts preview search as soon as the item title and description are available. When selected collector-number and expansion clues are present, the background worker runs the exact structured `/api/extension-card-search` path before autocomplete/name validation so perfect collector+set matches can render quickly. It does not wait for the final safe details anchor before sending `searchCardForTitle`.
21. Vinted preview searches are keyed by listing URL plus the selected clue signature, including selected collector-number and expansion chips. One in-flight search is shared for identical listing/clue inputs, stale responses are ignored, and cached results prevent identical repeated `searchCardForTitle` messages. Toggling a clue intentionally creates one new signature and runs exactly one new preview search.
22. When search results arrive before Vinted has finished loading the details anchor, the processor stores them by signature. The UI mounts later inside the safe detail container and immediately applies cached results without sending another search.
23. Each Vinted processing session records lightweight diagnostics on `window.__pokoinVintedDiagnostics`: stable listing key, search signature, trigger/reason, sequence id, duplicate skip reason, stale-response status, and anchor/UI mount status. These records are for debugging repeated same-page searches and avoid noisy per-selector console spam.

## Match Resolution Flow

1. The content script or side panel scrapes the marketplace title.
2. Local cleanup removes marketplace noise such as `pokemon`, `pokémon`, `carta`, `carte`, `card`, `cards`, `sealed`, `salead`, `pack`, `booster`, `lot`, `first edition`, `prima edizione`, and `1 edizione`.
3. Expansion aliases are preserved as structured expansion fields before name cleanup; for example Italian `set base` maps to `Base Set`, and Vinted `Evoluzioni` maps to `Evolutions`.
4. Candidate title terms are checked through Cardvault autocomplete.
5. A candidate name is accepted only when Cardvault returns an exact `canonical_name` or `name` match from the backend name tables. Across Cardmarket, Vinted, and eBay, exact/longest trainer or composite card names from those tables are preferred over shorter Pokemon-only matches.
6. The resolved name is sent to `/api/extension-card-search`.
7. Returned matches are accepted only if the returned card name still matches the resolved structured name.
8. If structured search returns no accepted rows, the extension falls back to marketplace autocomplete.
9. CardTrader card pages are supported directly: when the URL contains `/cards/:id`, that CardTrader blueprint id is used as the Pokoin card id without running search.
10. Plain `Nidoran` is treated as a special ambiguous name: keep both male and female candidates visible, and use expansion/collector evidence to rank the best one.
11. First-edition wording is a local ordering hint, not a hard expansion filter: boost the Base Set family (`Base Set`, `Base Set 2`, `Base Set Shadowless`) first, but keep newer Japanese/modern edition candidates available afterward.
12. Variation text such as `V`, `ex`, `VMAX`, and `VSTAR` is preserved in the Cardvault search name so the side panel uses the same more-specific matching behavior as the injected button.
13. On Vinted pages, compact clue chips are extracted from the item title and description. Useful clues include real Pokemon-name-like terms such as `Reshiram`, attached name/variation phrases such as `Regice ex` or `Mewtwo VSTAR`, collector numbers like `35/108`, promo codes, rarity/variation words, localized expansion aliases such as `Evoluzioni` -> `Evolutions`, and known expansion names; generic marketplace words like `carta`, `carte`, `card`, and `cards` are never shown as chips and never sent as search clues. The common Italian typo `vastro` is normalized to `vstar` before clues, request titles, and structured variation parsing.
14. Vinted clue chips are selected by default when they are the Pokemon name itself, a variation directly attached/adjacent to that Pokemon-name phrase, or high-confidence title evidence such as a collector number or expansion alias. For example `Regice Ex` selects `Regice ex` and `ex`; `Pikachu, Evoluzioni 35/108` selects `Pikachu`, `Evolutions`, and `35/108`; `Regice` with detached description text like `versione ex`, `vintage`, or `Set Ex` leaves those contextual chips off. Other useful but non-name-like clues still render as chips, but start off and only affect search after the user toggles them on.
15. Cardmarket product titles like `Piplup (MEP 042)` are parsed from the real page heading, preferring `.page-title-container h1`/`main h1` and removing extension-owned buttons, panels, inputs, and iframes before reading text. Text before the parenthesized code becomes the card name, the full code is kept as `collectorNumber` (`MEP 042`) with the numeric value (`042`) available for matching, the muted `h1 span` supplies the expansion after removing `- Singles` (`MEP Black Star Promos`), and localized detail rows such as Italian `Numero`, `Stampata in`, and `Specie` can reinforce collector number, expansion, and species. Exact heading identity wins over image/sidebar/search text, and exact name + collector-number + expansion matches rank above generic same-name rows, even when generic rows have higher backend scores. Trainer/composite names from Cardvault name tables are preferred over shorter Pokemon-only matches, so titles such as `Arven's Mabosstiff ex (mC 484)` resolve before any `Mabosstiff` fallback.
16. Side-panel refreshes always write a terminal state after Cardmarket scraping or search failures. Failures clear the loading state with empty candidates and an error message instead of leaving the panel stuck on the previous loading payload.
17. Low-candidate exact searches use a fast path. If the structured title already has exact identity evidence (`collectorNumber` plus expansion) or a concrete name plus variation such as `Tornadus EX`, the background worker calls `/api/extension-card-search` before Cardvault name-table autocomplete. When that returns rows, autocomplete fallback is skipped, candidates render immediately, and cached price enrichment plus Cardmarket scrape observation/auth continue asynchronously.
18. Background search debug metadata includes lightweight phase timings in `debug.phaseTimings` (`pageInfoMs`, `extensionSearchMs`, `nameResolutionMs`, `autocompleteFallbackMs`, and `totalMs` when applicable). Use these timings to distinguish page scraping, exact search, name resolution, fallback autocomplete, price enrichment, and Cardmarket observation delays without adding per-selector console noise.

## Candidate Display Flow

1. Candidate rows show compact metadata only: collector/card number, expansion name, and Pokoin listing price when available. Vinted intentionally hides the card name in preview rows because it repeats the listing/search name.
2. Collector metadata shows only the first collector number:
   - `SVP 129` becomes `129`
   - `232/091` becomes `232`
   - `Holo Promo | XY92` becomes `92`
3. Expansion metadata shows an explicit Cardvault expansion code when available.
4. If no explicit expansion code exists, use the collector prefix such as `SVP` or `XY`.
5. If no useful prefix exists, derive initials from the expansion name.
6. If no compact shortname can be derived, show the expansion name.
7. Vinted's preview and the side panel can show up to eight candidates without a visible "Best candidates" heading. The Vinted preview is scrollable when candidates overflow and its rows are clickable button side-panel openers. Selecting a preview row sends the chosen candidate id and metadata to the background worker, so an already-open side panel refreshes to that exact candidate instead of keeping the previous result order.
8. Vinted scrapes title, description, and detail context from the product DOM, including `h1.web_ui__Text__title`, `[itemprop="description"]`, `[data-testid="item-page-summary-plugin"]`, `.box--item-details`, and related item-detail containers. That DOM is a data source only; the extension UI is not inserted into the product details/title block.
9. Vinted clue chips live inside the overlay and wrap naturally there. Pokemon-name-like chips start on unless an attached name/variation phrase is available; in that case the phrase and its directly attached variation, including normalized `vastro` -> `vstar`, are the default-on name evidence. Collector numbers and expansion aliases present in the title also start on because they identify the printing. Contextual rarity and description clues such as `vintage`, detached `Set Ex`, or full-art/illustration hints start off unless the user toggles them. Changing a chip re-runs the background search and updates the same blue button state and candidate preview list used by side-panel resolution.
10. Vinted keeps one overlay root per listing. A MutationObserver watches for Vinted SPA rerenders that remove the host, then reattaches the same fixed overlay without duplicating panels, searches, or losing the current button/chip/candidate state. Vinted-specific navigation watching detects true listing URL changes and resets the guard so the new listing renders and searches once.
11. The Vinted overlay sits at the lower-left viewport edge to avoid covering the listing content and remains isolated from Vinted CSS.
12. Expansion logos only decorate candidate rows when available. They do not reorder side-panel results; candidate order remains the order returned by the background/API ranking.
13. The background service worker enriches up to eight returned candidates with a cached lookup to `/api/cardtrader-redirect?id=:blueprintId` and reads the first formatted product listing price. Price lookup failures are ignored, and Vinted preview plus side-panel candidates render before price enrichment completes so marketplace inventory data cannot block the initial match list.
14. Cardmarket scrape observations are also non-blocking for rendering/search responses. Missing Pokoin auth may queue the observation and open the auth bridge, but that work happens after the side-panel or preview response has already been written.

## Processor Boundaries

Marketplace processors are responsible for page detection, button placement, lightweight preview UI, and sending `searchCardForTitle` / `openSidePanelForCurrentTab` messages. The background service worker owns Cardvault search, fallback autocomplete, and the canonical side-panel payload: `pageInfo`, `rows`, `best`, `blueprintId`, `pokoinUrl`, `error`, and debug metadata. Processors should not open Pokoin cards directly, should not depend on having a resolved candidate before wiring the side-panel click handler, and should not add direct Supabase/database lookups.

Some older content-script APIs still use database-era names such as `searchCardInDatabase` and return result objects with legacy field names like `blueprint_id` for processor compatibility. Those adapters now call Pokoin/Cardvault endpoints (`/api/extension-card-search` and `/api/marketplace-autocomplete`); they are not Supabase integration points.

eBay and Cardmarket processors attach the side-panel click handler as soon as the gray button is created, then only update visual state after matches arrive. Vinted additionally sends selected clue chips and primary Pokemon-name-like clues. CardTrader sends the blueprint id directly and lets the background service worker write a complete direct-card side-panel state.

The background `searchCardForTitle` path also de-dupes identical active requests by stable URL, title, and clue signature. This protects the backend if a content script and processor both send the same search, while still allowing manual side-panel refreshes and clue changes to resolve with fresh state when their inputs differ.

## CardTrader Direct Path

CardTrader was slower when the side panel opened because the background service worker still executed the generic page-title scraping path before it noticed the URL contained a blueprint id. The direct path now checks CardTrader URLs before injecting any page script or calling Cardvault APIs, writes the side-panel state with `source: cardtrader_url`, and opens the common side panel immediately.

When direct CardTrader state is rendered, the side panel treats it as a full card page view only for CardTrader direct URLs: candidates remain hidden, the panel body removes its normal padding, and the embedded Pokoin card page fills the available side-panel width and height under the header. Other marketplace side panels keep the normal candidate and iframe layout. The header uses a clean card name from the page title, structured card data, or URL slug fallback. The same cleanup is used for direct CardTrader preview/search responses, so URL-like titles and verbose parenthesized expansion/category/site suffixes never leak into the side-panel header or candidate payload.

CardTrader direct state is also locked to the URL blueprint id. Once the side-panel state contains a CardTrader `/cards/:id` URL and matching `blueprintId`, scheduled refreshes for the same URL are ignored instead of writing a loading state or running the generic scrape/search path. Delayed refreshes from a previous marketplace page re-check the live tab URL and the latest side-panel state before writing, so an older search result cannot replace the direct CardTrader iframe. Navigating to a different CardTrader card URL is still allowed to update the lock to the new blueprint id.
