# Extension Workflow

## Button Click Flow

1. Marketplace content scripts add a Pokoin button to supported listing pages.
2. Buttons are created immediately in a gray/loading state and still open the Chrome side panel. A resolved match is not required before the user can click.
3. When matches arrive, the button shows `Pokoin.com (N)`, where `N` is the count of matches above the high-confidence threshold. Vinted keeps the Pokoin brand blue in both empty and matched states. Cardmarket switches from a compact gray loading state to a compact bright-blue matched state with a visible border/glow.
4. Clicking any marketplace button opens the Chrome side panel for the current tab instead of opening a new browser tab.
5. The background service worker refreshes the side panel state for the sender tab.
6. The side panel embeds the Pokoin marketplace card page so the user's Pokoin login session stays inside the panel.
7. Marketplace processors use the background service worker as the reliable Cardvault search path. There is no active Supabase client, `config/supabase` module, or direct database lookup in the extension.
8. Button clicks and navigation refreshes claim side-panel ownership with a monotonic request id for the current tab and URL. Each new active tab or URL cancels the previous pending owner, clears stale rows before generic searches, and only the latest owner can write `sidePanelState`; older async search, scrape, timer, or price-enrichment completions are ignored with debug metadata (`sidePanelRequestId`, tab id, URL, reason, and stale ignored count).
9. Vinted, eBay, Cardmarket, and CardTrader all use this same button -> background refresh -> side panel render workflow.
10. Vinted and eBay pass selected overlay clues with preview searches and button clicks. Those selected chips are the canonical first layer for both marketplaces: name-like chips, explicit variations, Mega X/Y form tokens, collector numbers, expansions, and feature chips build the structured search payload before any page-title fallback is considered. Meaningful title words also render as manual chips, but unselected title words are not added to primary search evidence while selected chips exist.
11. CardTrader card URLs already contain the Pokoin/CardTrader blueprint id, so CardTrader button clicks construct side-panel state immediately from the URL id and do not wait for page scraping, Cardvault name resolution, extension search, or autocomplete.
12. Direct CardTrader state stores a human card name for the side-panel header. The header keeps only the card name and real card-name punctuation/variation, such as `Hypno`, `Gengar & Mimikyu GX`, or `Tornadus-EX`, and drops parenthesized expansion/rarity/collector/promo details plus pipe/category/site suffixes from CardTrader titles and URL slugs.
13. CardTrader injects the Pokoin button as a real `type="button"` beside the card title and handles click events in capture phase. The handler prevents default page actions, stops propagation, ignores duplicate clicks while an open request is in flight, and sends a single side-panel message instead of letting CardTrader links/forms/navigation handlers react.
14. Cardmarket buttons are styled as compact inline controls in both gray/loading and bright-blue matched states. Product-page injection waits until Cardmarket has hydrated the stable title container and product identity details (`.page-title-container h1` plus `dl.labeled` fields such as `Numero` and `Stampata in`, or an equivalent expansion link) before inserting into the title action area such as `.ms-auto`. The processor sends the title plus detail-derived collector/expansion clues to the background worker, so the button preview and side-panel open path use the same exact Cardmarket identity. If hydration or AJAX removes the control, a short MutationObserver/retry path re-injects it for the same stable product URL without launching duplicate searches. Relabeling the button after matches are found reapplies the matched color, border/glow, and small Pokoin icon sizing so the raw icon asset cannot stretch across the product image area.
15. `processors/CME.js` is the only active Cardmarket content-script path. The historical `content.js` Cardmarket product-page fallback remains defined only as an inert compatibility stub and returns before inserting buttons or sending searches. This avoids a second title-only Cardmarket workflow racing the readiness-gated processor.
16. The background worker stamps side-panel state with a runtime marker (`extensionVersion` and `buildMarker`). On a build marker change it clears in-memory search/name caches and invalidates stale `chrome.storage.session.sidePanelState`, so a loaded extension cannot keep showing candidates from the previous service-worker build.
17. Cardmarket side-panel state is protected by exact-result priority. Once the state for a Cardmarket URL contains exact structured identity (`collectorNumber` plus expansion) and a selected/best Pokoin card id, later same-URL updates that only contain a name/title cannot overwrite it. Price enrichment may update the same exact card, but generic title-only rows cannot replace it.
18. If the Cardmarket DOM scrape is degraded or too early, the background worker can derive exact identity from the product URL slug, for example `/Singles/MEP-Black-Star-Promos/Piplup-MEP042` becomes `Piplup (MEP 042)` with expansion `MEP Black Star Promos`. This is a fallback identity source, not a second content-script search path.
19. Cardmarket collector matching keeps the printed padded collector as the primary identity. Values such as `DRS 009`, `MEP 042`, `CP5 026`, `POR 062`, and `SVP 121` stay padded in structured fields, extension-search payloads, and exact-ranking comparisons; numeric equivalence such as `009` equals `9` is only a lower-ranked fallback for unpadded marketplace/API rows.
20. The packaged `dist/pokemon-card-extension-2.0.0.zip` is treated as a runtime artifact, not a source of truth. Tests compare hashes for runtime files in the zip against source files (`manifest.json`, `content.js`, `config/background.js`, `processors/CME.js`, and side-panel assets) so stale packaged content cannot pass unnoticed.
21. Cardmarket scrape observations are sent from the background worker to `POST https://pokoin.com/api/cardmarket-scrape-observation`. The payload contains the parsed `structuredCard`, `cardmarketContext`, selected or best `match`, and `promoteVerifiedLink`. Navigation/search observations are non-promoting; opening the side panel from a matched Cardmarket candidate promotes the verified link and allows Pokoin to store the full Cardmarket URL in `marketplace_cm_verified_links`.
22. Auth for Cardmarket observations uses a minimal Pokoin-origin bridge at `https://pokoin.com/extension/auth-bridge`. The extension injects `pokoin-auth-bridge.js` only on that path, requests a Firebase ID token with `postMessage`, accepts token responses only from `https://pokoin.com`, and stores the token in `chrome.storage.session` with expiry metadata. After a valid token is stored and queued observations are flushed, the background worker closes the tracked auth bridge tab when it was opened by the extension or is still on the exact bridge path. Normal Pokoin marketplace/card tabs are never closed by this cleanup. The token is reused until it is near expiry; the bridge is lazy and is not opened when a fresh session token exists. The token is never stored in `chrome.storage.local` and is not exposed to marketplace content scripts.
23. If a Cardmarket observation is ready before a Pokoin token is available, the background worker queues a small bounded session-only pending observation and opens or reuses the bridge tab asynchronously in the background. Concurrent token requests share one in-flight request, and missing/expired auth never blocks preview search, side-panel matching, or the terminal side-panel state write. When a valid token arrives, pending observations are flushed with `Authorization: Bearer <token>`.
23. `processors/VINT.js` is the single source of truth for Vinted matching. It extracts the item title and description, builds categorized clue chips (`name`, `variation`, `collector`, `expansion`, `feature`, and `context`), selects default Pokemon/variation/title collector/expansion clues, and sends one canonical `searchCardForTitle` request to the background for the current stable listing URL plus selected clue signature. The historical `content.js` Vinted product-page fallback is inert and must not scrape, search, or insert Vinted buttons while this processor owns the page.
24. Vinted renders its Pokoin button, clue chips, and candidate preview in a compact transparent fixed overlay marked with `data-pokoin-extension-panel`. The overlay uses Shadow DOM when available and has one root per stable listing URL. Repeated `processProductPage()` calls, MutationObserver callbacks, same-listing SPA rerenders, and collapse/expand changes reuse the existing root, cached preview rows, and selected clue state instead of creating another search path.
25. Vinted preview rows are the canonical candidate list, and they are downstream of the overlay token scanner. After title/description scanning and chip selection, the processor emits a token-ready `marketplacePreviewReady` message with the stable listing key, selected clues, structured `vintedPayload`, and preview signature; after the overlay search applies results, the same message also includes `previewRows`. The background caches this Vinted-ready state per tab and URL. Clicking a candidate selects that card for the side-panel iframe, but it does not reorder or collapse the full candidate list. When selected Vinted chips exist, background name resolution, exact search, fallback autocomplete, side-panel open, side-panel Refresh, and extension action-click all use the selected-chip search title rather than the raw listing title.
26. The background seeds Vinted side-panel state from canonical `previewRows`, or from the token-ready `vintedPayload` when rows are not available yet. Vinted URL changes, extension action-clicks, and the side-panel Refresh button do not run the broad active-tab scrape while the processor is still hydrating; they either reuse cached canonical overlay tokens/rows or write a lightweight `waiting for Vinted tokens` loading state until token-ready arrives. If token-ready never arrives, the panel settles on `Waiting for Vinted listing details` rather than broad-searching with wrong keywords. A new exact Vinted search happens only after the processor sends selected tokens for the current clue signature, such as after a chip toggle or true listing change.
27. Vinted price enrichment is decoration only. It may add `pokoin_price` to the same pinned rows, but it cannot reorder rows, replace rows with autocomplete results, or change the selected/best card except to keep the already selected preview card current.
28. Opening the Vinted side panel uses the same result source as the left overlay preview. The content script sends the selected clue chips, primary clues, structured Vinted payload, preview signature, preview source, and the currently ranked preview rows with the main Pokoin button or candidate-row open request. The structured payload carries deterministic fields (`name`, `variation`, `collectorNumber`, `numericCollectorNumber`, `expansion`, `features`, and `rarity`) so the background can seed search and side-panel state from Vinted's selected chips instead of re-parsing page text. Promo collectors such as `PROMO 159` remain atomic collector clues and are carried into both preview search and side-panel open payloads. Weaker broad re-scrapes, tab activation, tab-complete refreshes, stale owner completions, and storage-change rerenders cannot replace the overlay candidate set for the same URL; auto-refresh is a consumer of canonical overlay state, not a broader search source. Vinted also hard-bounds every image inside the overlay root and button header so the Pokoin logo asset can only render as a small icon, never at natural image size.
29. eBay product pages now follow the same selected-key overlay workflow as Vinted. The eBay processor renders a transparent fixed overlay with the Pokoin button, key chips, and candidate preview rows; selected name/variation/collector/expansion chips build the structured payload (`name`, `variation`, `collectorNumber`, `numericCollectorNumber`, `expansion`, `features`, and `rarity`) and a revisioned search signature. Chip toggles clear stale preview rows and only apply the latest background response. eBay listing-feed buttons remain compact, but product-page side-panel opens reuse the overlay payload and preview rows instead of broad re-parsing.
30. Cardmarket follows the same preview parity rule. When the product button search resolves candidates, the processor caches those rows by stable product URL and sends them as `previewRows` with the button click. The side panel renders those rows immediately and pins them for that URL, so later Cardvault name, fallback, price, or observation request failures cannot turn a matched `Pokoin.com (N)` button into an empty panel.
31. The Vinted overlay header keeps the main `Pokoin.com` button and a square collapse control in the same row. Expanded state keeps the main label as `Pokoin.com` without a result suffix; collapsed state hides clue chips and preview rows while the main label changes to the current result count such as `8 matches`, with the square control acting as the compact reopen affordance.
32. Each Vinted processing session records lightweight diagnostics on `window.__pokoinVintedDiagnostics`: navigation, title-ready, tokens-ready, preview-ready, stable listing key, search signature, trigger/reason, sequence id, duplicate skip reason, stale-response status, anchor/UI mount status, selected chip categories, and the structured Vinted payload used for background search or side-panel open. These records are for debugging repeated same-page searches and avoid noisy per-selector console spam.

## Match Resolution Flow

1. The content script or side panel scrapes the marketplace title.
2. Local cleanup removes marketplace noise such as `pokemon`, `pokémon`, `carta`, `carte`, `card`, `cards`, `sealed`, `salead`, `pack`, `booster`, `lot`, `first edition`, `prima edizione`, and `1 edizione`.
3. Expansion aliases are preserved as structured expansion fields before name cleanup; for example Italian `set base` maps to `Base Set`, and Vinted `Evoluzioni` maps to `Evolutions`.
4. If selected chips or scraped payloads already have strong exact evidence, the background calls `/api/extension-card-search` first with the selected name/variation/collector/expansion.
5. If that exact path is empty or weak, the background first tries `POST /api/searchbar-token-predict` for a lightweight card-name token. Accepted predictions must extend the scraped fragment and meet the confidence threshold; the background then retries `/api/extension-card-search` with that clean token and the original collector, expansion, rarity, and variation fields.
6. If token prediction is empty, low-confidence, or unavailable, the background resolves likely name phrases through `POST /api/marketplace-autocomplete`. This is the Cardvault name-index path: it sends `search_term`, `result_limit: 20`, a query-length pool limit, `search_language: "en"`, and a generated `search_session_id`.
6. Resolver results are cached by normalized query, language, source, and selected clue signature, so tab switches, refreshes, and unchanged selected payloads do not repeat the same autocomplete call.
7. The resolver only probes likely card-name phrases. Standalone feature/context/set/condition tokens such as `holo`, `delta`, `illustration`, `liv 53`, expansion names, grades, and collector numbers are not sent as primary name-resolution queries.
8. A candidate name is accepted from backend autocomplete rows, with trainer/composite names preferred over shorter species names. Across Cardmarket, Vinted, and eBay, exact/longest names such as `Team Rocket's Mimikyu`, `Rocket Zapdos`, or `Arven's Mabosstiff ex` are preserved.
9. The canonicalized name is retried through `/api/extension-card-search` while preserving collector, expansion, rarity, and variation constraints.
10. If structured search still returns no accepted rows, marketplace autocomplete becomes the broader fallback candidate source.
9. CardTrader card pages are supported directly: when the URL contains `/cards/:id`, that CardTrader blueprint id is used as the Pokoin card id without running search.
10. Plain `Nidoran` is treated as a special ambiguous name: keep both male and female candidates visible, and use expansion/collector evidence to rank the best one.
11. First-edition wording is a local ordering hint, not a hard expansion filter: boost the Base Set family (`Base Set`, `Base Set 2`, `Base Set Shadowless`) first, but keep newer Japanese/modern edition candidates available afterward.
12. Variation text such as `Mega`, `V`, `ex`, `VMAX`, and `VSTAR` is preserved in the Cardvault search name so the side panel uses the same more-specific matching behavior as the injected button.
13. On Vinted and eBay product pages, compact clue chips are extracted from the item title and available description/detail text. Useful clues include real Pokemon-name-like terms such as `Reshiram` or `Sylveon`, composite/specific card names such as `Rocket Zapdos`, `Dark Magneton`, `Alto Mare's Latias`, `Holon's Magneton`, `Gengar Mimikyu GX`, `Espeon & Deoxys ex`, `Team Rocket's Mimikyu`, and `Arven's Mabosstiff ex`, attached name/variation phrases such as `Regice ex`, `Magnezone V`, or `Mewtwo VSTAR`, collector numbers like `35/108`, promo codes, rarity/variation words, localized expansion aliases such as `Evoluzioni` -> `Evolutions`, and known expansion names; generic marketplace words like `carta`, `carte`, `card`, and `cards` are never shown as chips and never sent as search clues. Every meaningful title token remains clickable when it is not pure marketplace/condition noise, including individual words beside a selected composite, while collector tokens stay atomic with slash or prefix evidence (`TG16/TG30`, `RC32/RC32`, `SVP 129`, `BW96`). Attached text such as `holo50/99` is split so the feature word and normalized collector number can be selected independently. eBay prefixed slash collectors such as `RC32/RC32` stay atomic and infer Radiant Collection/Generations evidence when present. When a valid composite, tag-team, trainer, or owner/team card name appears in the title, it is preferred as the primary name over shorter species chips, so `Rocket Zapdos 15/132` searches as `Rocket Zapdos` with collector `15/132`, `Espeon e deoxys ex` searches as `Espeon & Deoxys ex`, `Mimikyu del Team Rocket` searches as `Team Rocket's Mimikyu`, and trainer composites such as `Arven's Mabosstiff ex` are preserved across marketplace paths. The common Italian typo `vastro` is normalized to `vstar` before clues, request titles, and structured variation parsing. Pokemon names should normally be validated through Cardvault autocomplete/name-index resolution; local fuzzy matching is only a parser hint, and Vinted keeps only small targeted local typo aliases when the name table cannot recover a frequent listing typo, such as `Magaerna`/`Magaeran` -> `Magearna`.
14. Vinted clue chips are selected by default when they are the Pokemon name itself, a validated composite/tag-team phrase, a variation directly attached/adjacent to that name phrase, or high-confidence title evidence such as a collector number or expansion alias. Collector/card codes are extracted before text n-grams and stay atomic, so examples such as `SV 11b 137`, `35/108`, `MEP 042`, `TR 62`, and `CP5 026` render as one clean chip instead of noisy adjacent fragments. Bare numeric collectors such as `194` also render as collector chips when the listing has card-like context or a nearby card name, and those numbers suppress overlapping context fragments such as `it 194` and `194 appena`. For example `Regice Ex` selects `Regice ex` and `ex`; `Mega Latias Ex` selects `Mega Latias ex`, `Mega`, and `ex`; `Mega Charizard X ex 13/94` selects `Charizard`, `Mega`, `X`, `ex`, and `13/94`, with `X`/`Y` only defaulting inside a Mega-form context; `Magnezone V 056/196` selects `Magnezone V`, `V`, and `056/196`; `Pikachu volo VMAX 007/025` selects `Pikachu`, `VMAX`, and `007/025` without promoting noisy `volo` composites; `Pikachu, Evoluzioni 35/108` selects `Pikachu`, `Evolutions`, and `35/108`; `Regice` with detached description text like `versione ex`, `vintage`, or `Set Ex` leaves those contextual chips off. Explicit variations (`Mega`, `V`, `VMAX`, `VSTAR`, `ex`, `EX`, `GX`, `X`, `Y`, etc.) remain distinct in the structured payload, and background ranking rejects returned rows with a missing or conflicting explicit variation/form for exact collector+variation requests so selected `Mega`/`X`/`Y`/`VMAX`/`V` cards are not replaced by broad Pokemon-only or unrelated named cards. An `illustration` chip is always visible for manual selection, but starts selected only when the title directly contains `fullart`, `full art`, or `illustration`. Other useful but non-name-like clues still render as chips, but start off and only affect search after the user toggles them on.
15. Cardmarket product titles like `Piplup (MEP 042)` are parsed from the real page heading, preferring `.page-title-container h1`/`main h1` and removing extension-owned buttons, panels, inputs, and iframes before reading text. Text before the parenthesized code becomes the card name, the full code is kept as `collectorNumber` (`MEP 042`) with the numeric value (`042`) available for matching, the muted `h1 span` supplies the expansion after removing `- Singles` (`MEP Black Star Promos`), and localized detail rows such as Italian `Numero`, `Stampata in`, and `Specie` can reinforce collector number, expansion, and species. Exact heading identity wins over image/sidebar/search text, and exact name + collector-number + expansion matches rank above generic same-name rows, even when generic rows have higher backend scores. Trainer/composite names from Cardvault name tables are preferred over shorter Pokemon-only matches, so titles such as `Arven's Mabosstiff ex (mC 484)` resolve before any `Mabosstiff` fallback.
16. Side-panel refreshes always write a terminal state after Cardmarket scraping or search failures. Failures clear the loading state with empty candidates and an error message instead of leaving the panel stuck on the previous loading payload.
17. Low-candidate exact searches use a fast path. If the structured title already has collector evidence plus a card name, exact identity evidence (`collectorNumber` plus expansion), or a concrete name plus variation such as `Tornadus EX`, the background worker calls `/api/extension-card-search` before Cardvault name-table autocomplete. Cardmarket localized expansion aliases are normalized centrally before that call; for example Italian `Equilibrio Perfetto` maps to `Perfect Order`, `Caos Nascente` maps to `Chaos Rising`, and `EX Leggende Nascoste` maps to `EX Hidden Legends`. The Cardmarket h1 collector shape remains the printed collector (`HL 9`, `DRS 009`, `MEP 042`, `TR 62`) while `Numero` remains the numeric display value (`9`, `009`, `042`, `62`) for secondary matching and debug. For prefixed Cardmarket set codes that the API matches by printed number, such as `POR 062` and `TR 62`, the API payload uses the numeric collector (`062` or `62`) while preserving the printed value for ranking/display. When the exact API returns good-enough exact rows, meaning the returned candidates include the requested exact name or name+variation plus matching numeric/prefixed collector and any requested expansion alias/code, those rows are final even when there are fewer than eight candidates. Strong exact rows are filtered to exact-name or explicit variation rows, so `Machamp (HL 9)` cannot be replaced by `Machamp VMAX` or other name-only variants, and `Pikachu VMAX 007/025` cannot be replaced by `Pitch's Pikachu` or plain `Pikachu`. Weak name-only or empty exact rows still continue through name resolution and fallback.
18. When selected marketplace clues contain strong collector evidence but the selected/title name cannot be validated as an exact Cardvault name, the background runs a collector-number-first recovery pass. That pass searches by collector plus expansion/set clues, infers the corrected name only from number-compatible rows when the candidate identity is unambiguous, and then re-ranks with the corrected structured name. This lets misspelled titles such as `Zecrom holo50/99` recover a `Zekrom`-compatible `050/99` row instead of letting the misspelled species dominate or falling through to unrelated high-score cards. Numeric-only equivalence is still lower confidence than exact prefixed/slash collector evidence and is used only to bridge padding differences such as `50/99` versus `050/99`.
18. Background search debug metadata includes lightweight phase timings in `debug.phaseTimings` (`pageInfoMs`, `extensionSearchMs`, `nameResolutionMs`, `extensionSearchAfterResolutionMs`, `autocompleteFallbackMs`, and `totalMs` when applicable). `nameResolutionMs` measures the cached Cardvault autocomplete/name-index canonicalization step, while `autocompleteFallbackMs` is the later broad candidate-fill fallback. The side panel renders these timings under the runtime marker so page scraping, exact search, name resolution, fallback autocomplete, price enrichment, and Cardmarket observation delays are visible without adding per-selector console noise.

## Database-Informed Collector Numbers

Cardvault stores collector evidence in several shapes, and the extension must preserve the strongest printed form before falling back to numeric comparison. Representative local Cardvault docs, tests, and Cardmarket seed examples include slash totals (`007/025`, `35/108`, `025/165`, `232/091`), gallery slash codes (`TG16/TG30`, `RC32/RC32`), rarity-prefixed stored values (`Special Illustration Rare | 232/091`, `Illustration Rare | 204/191`, `Holo Promo | XY67a`), promo codes (`BW96`, `XY141`, `SM194`, `SWSH270`, `SVP 129`, `SV-P 129`), and Cardmarket/product-set tuples (`DRS 009`, `HL 9`, `MEP 042`, `POR 062`, `CP5 026`, `CSM1cC | 143/151`, `WCD 2018 | ... | 057/111`).

Marketplace processors treat the full collector token as atomic evidence. Vinted and eBay keep prefixed numbers with their separator (`DRS 009`, `HL 9`, `SV-P 129`) and compact gallery slash codes without splitting off the prefix (`TG16/TG30`, `GG70/GG70`, `RC32/RC32`). The background structured parser uses that full value for `collectorNumber`, `printedCollectorNumber`, search queries, extension-card-search payloads, side-panel debug, and exact ranking. `numericCollectorNumber` remains available for lower-confidence fallback and unpadded data, but numeric-only equivalence must never outrank an exact printed/prefixed collector match.

## Search Accuracy Rules

Recent marketplace failures show that broad title search should be the last resort, not the default. Vinted and eBay must first search from selected overlay keys, then from structured exact evidence, and only then from fallback title text. The current high-confidence order is:

1. Exact collector number plus expansion/set clue, such as `TG16/TG30` + `Lost Origin`, `RC32/RC32` + `Radiant Collection`, `14/100` + `EX Sandstorm`, or `DRS 009` + `Dragon Selection`.
2. Validated composite or owner/team card name, such as `Team Rocket's Mimikyu`, `Rocket Zapdos`, `Espeon & Deoxys ex`, `Arven's Mabosstiff ex`, or `Alto Mare's Latias`.
3. Explicit variation/form evidence attached to the selected name, such as `Mega + X + ex`, `Mega + ex`, `VMAX`, `VSTAR`, `V`, `GX`, or `ex`.
4. Rarity/feature evidence, such as `illustration`, only after expanding it into backend-compatible rarity aliases.
5. Broad species/name fallback, only when stronger selected keys are absent or have produced no usable rows.

When selected chips exist, unselected title words must not leak into the primary search payload. Words such as `volo`, condition text, grading text, seller notes, and category words can remain visible as manual chips if useful, but they should not affect matching until selected. Chip toggles and side-panel refreshes must snapshot the current highlighted chips and invalidate stale preview rows, so an older `Gengar` or `Mimikyu` result cannot overwrite a newer `Pikachu`, `Zekrom`, or `Sprigatito` search.

Collector evidence should be used to recover from misspellings. If a title has a weak or misspelled name (`Zecrom`) but strong number evidence (`050/99`, `099`, `TG16/TG30`, `RC32/RC32`), the background should search by collector plus expansion first, infer the corrected name only from number-compatible rows, and then rerank. Number-only recovery is useful, but ambiguous number-only matches should show multiple candidates rather than forcing a wrong best row.

Rarity chips need backend aliases. The UI may keep one simple `illustration` chip, but the structured search should expand it before calling Cardvault:

- `illustration` -> `Illustration Rare`
- `illustration` -> `Special Illustration Rare`
- `illustration` -> `full art`
- `illustration` -> `illustration`

For a selected `Sprigatito + illustration` search, `/api/extension-card-search` should receive either an alias-aware rarity field or multiple exact attempts such as `Sprigatito Illustration Rare` and `Sprigatito Special Illustration Rare`. Ranking should prefer rows whose `rarity`, stored collector prefix, or product metadata contains `illustration` over generic same-name rows. This avoids the current failure mode where `rarity: "illustration"` is too generic for backend rows stored as `Illustration Rare` or `Special Illustration Rare`.

Implementation guidance for future changes:

- Keep UI chip labels short, but preserve structured payload detail (`name`, `variation`, `variationTokens`, `collectorNumber`, `expansion`, `features`, `rarityAliases`).
- Add exact tests before tuning: one processor payload test, one background ranking test, and one packaged-zip hash test when runtime files change.
- Prefer adding aliases to shared normalization/ranking helpers over marketplace-specific one-off branches, unless the evidence is truly site-specific.
- Treat price enrichment, auth observations, and fallback autocomplete as decoration or recovery. They must not reorder or replace rows that were selected by stronger overlay evidence.

## Candidate Display Flow

1. Candidate rows show compact metadata only: collector/card number, expansion name, and Pokoin listing price when available. Vinted intentionally hides the card name in preview rows because it repeats the listing/search name.
2. Collector metadata shows only the first collector number:
   - `SVP 129` becomes `129`
   - `232/091` becomes `232`
   - `Holo Promo | XY92` becomes `92`
3. Expansion metadata shows an explicit Cardvault expansion code when available.
4. If no explicit expansion code exists, use the collector prefix such as `SVP` or `XY`.
5. If no useful prefix exists, derive initials from the expansion name.
6. If no compact shortname can be derived, show the expansion name.
7. Vinted's preview and the side panel can show up to eight candidates without a visible "Best candidates" heading. The Vinted preview is scrollable when candidates overflow and its rows are clickable button side-panel openers. Selecting a preview row sends the chosen candidate id and metadata to the background worker, so an already-open side panel refreshes to that exact candidate instead of keeping the previous result order.
8. Vinted scrapes title, description, and detail context from the product DOM, including `h1.web_ui__Text__title`, `[itemprop="description"]`, `[data-testid="item-page-summary-plugin"]`, `.box--item-details`, and related item-detail containers. That DOM is a data source only; the extension UI is not inserted into the product details/title block.
9. Vinted clue chips live inside the overlay and wrap naturally there. Pokemon-name-like chips start on unless an attached name/variation phrase is available; in that case the phrase and its directly attached variation, including normalized `vastro` -> `vstar`, are the default-on name evidence. Collector numbers and expansion aliases present in the title also start on because they identify the printing. Contextual rarity and description clues such as `vintage` or detached `Set Ex` start off unless the user toggles them, and the fixed `illustration` chip follows the same rule unless the title itself contains full-art/illustration wording. The chip limit preserves required feature chips such as `illustration` instead of letting later context n-grams crowd them out. Changing a chip re-runs the background search and updates the same blue button state and candidate preview list used by side-panel resolution.
10. Vinted keeps one overlay root per listing. A MutationObserver watches for Vinted SPA rerenders that remove the host, then reattaches the same fixed overlay without duplicating panels, searches, or losing the current button/chip/candidate state. Vinted-specific navigation watching detects true listing URL changes and resets the guard so the new listing renders and searches once.
11. The Vinted and eBay overlays sit at the top-left viewport edge, with the Pokoin button and clue menu anchored together. Their broad fixed hosts are click-through, and only the visible panel/buttons receive pointer events.
12. Expansion logos only decorate candidate rows when available. They do not reorder side-panel results; candidate order remains the order returned by the background/API ranking.
13. The background service worker enriches up to eight returned candidates with a cached lookup to `/api/marketplace-blueprint-price?blueprintId=:blueprintId` and formats `price_pkn` as PKN. A 404 or null price means there is no active Pokoin seller price; price lookup failures are ignored, and Vinted preview plus side-panel candidates render before price enrichment completes so marketplace inventory data cannot block the initial match list.
14. Cardmarket scrape observations are also non-blocking for rendering/search responses. Missing Pokoin auth may queue the observation and trigger the lazy auth bridge, but that work happens after the side-panel or preview response has already been written and cannot leave the panel in a loading state.

## Processor Boundaries

Marketplace processors are responsible for page detection, button placement, lightweight preview UI, and sending `searchCardForTitle` / `openSidePanelForCurrentTab` messages. The background service worker owns Cardvault search, fallback autocomplete, and the canonical side-panel payload: `pageInfo`, `rows`, `best`, `blueprintId`, `pokoinUrl`, `error`, and debug metadata. Processors should not open Pokoin cards directly, should not depend on having a resolved candidate before wiring the side-panel click handler, and should not add direct Supabase/database lookups.

Some older content-script APIs still use database-era names such as `searchCardInDatabase` and return result objects with legacy field names like `blueprint_id` for processor compatibility. Those adapters now call Pokoin/Cardvault endpoints (`/api/extension-card-search` and `/api/marketplace-autocomplete`); they are not Supabase integration points. Vinted is the exception: its legacy content-script product-page fallback is disabled, so Vinted candidates can only originate from `VintedProcessor` plus the background search it invokes.

eBay, Vinted, and Cardmarket processors attach the side-panel click handler as soon as the button is created, then only update the result count after matches arrive. Vinted and eBay render selectable clue chips in their top-left overlays and send the same structured selected-key payload shape. CardTrader sends the blueprint id directly and lets the background service worker write a complete direct-card side-panel state.

The background `searchCardForTitle` path also de-dupes identical active requests by stable URL, title, and clue signature. This protects the backend if a content script and processor both send the same search, while still allowing manual side-panel refreshes and clue changes to resolve with fresh state when their inputs differ.

## CardTrader Direct Path

CardTrader was slower when the side panel opened because the background service worker still executed the generic page-title scraping path before it noticed the URL contained a blueprint id. The direct path now checks CardTrader URLs before injecting any page script or calling Cardvault APIs, writes the side-panel state with `source: cardtrader_url`, and opens the common side panel immediately.

When direct CardTrader state is rendered, the side panel treats it as a full card page view only for CardTrader direct URLs: candidates remain hidden, the panel body removes its normal padding, and the embedded Pokoin card page fills the available side-panel width and height under the header. Other marketplace side panels keep the normal candidate and iframe layout. The header uses a clean card name from the page title, structured card data, or URL slug fallback. The same cleanup is used for direct CardTrader preview/search responses, so URL-like titles and verbose parenthesized expansion/category/site suffixes never leak into the side-panel header or candidate payload.

CardTrader direct state is also locked to the URL blueprint id. Once the side-panel state contains a CardTrader `/cards/:id` URL and matching `blueprintId`, scheduled refreshes for the same URL are ignored instead of writing a loading state or running the generic scrape/search path. Delayed refreshes from a previous marketplace page re-check the live tab URL and the latest side-panel state before writing, so an older search result cannot replace the direct CardTrader iframe. Navigating to a different CardTrader card URL is still allowed to update the lock to the new blueprint id.
